# DevOps Platform 研发操作手册

本文档面向研发人员，详细说明三个核心功能的操作流程、按钮含义及后端实现逻辑。

---

## 一、投产征集

**访问地址**：`/branch-create/release-entry/`

投产征集是研发人员在投产批次下填写投产行项（ReleaseItem）的入口，每个行项记录一条投产变更所需的所有上线信息。

### 1.1 研发操作填写流程

#### 步骤 1：选择投产批次

进入页面后，系统自动选中今天及之后最近的批次。可通过顶部下拉框手动切换。

- 批次状态为 **open（开放填写）** 时，研发才可新增/编辑行项
- 批次状态为 **closed** 时，研发不可再修改（管理员可重新开放）
- 批次状态为 **executed** 时，批次已完结，不可变更

#### 步骤 2：打开填写表单

点击 **「填写记录」** 按钮，弹出悬浮表单，包含四个区域：

**（1）基础信息**

| 字段 | 必填 | 说明 |
|------|------|------|
| 工程名称 | 是 | 下拉选择，来源于当前批次的工程列表 |
| 流程/功能名称 | 是 | 本次变更的名称 |
| 业务种类 | 是 | 业务分类 |
| 需求分支 | 条件必填 | 仅 SQL 上线可不填，其他情况必填 |
| 投产分支 | 自动 | 由批次决定，不可编辑 |
| 科技联系人 | 是 | — |
| 业务联系人 | 是 | — |
| 公共组件配合（分支） | 否 | — |
| 流程定义名称 | 条件必填 | 涉及流程图时必填 |
| 实施单元编号 | 否 | 选填 |
| 备注 | 否 | 选填，最多 255 字 |

**（2）bug修复信息**

| 字段 | 必填 | 说明 |
|------|------|------|
| 是否为bug修复 | 是 | 下拉选择"是/否/未填写"，无默认值 |
| bug修复汇报人 | 条件必填 | 选"是"时必填，多选（周子健/高翔），逗号分隔存储 |
| bug发现时间 | 条件必填 | 选"是"时必填，datetime-local 控件，精确到小时 |

**（3）检查项**

每个检查项均为三态下拉框（未填写 / 是 / 否），共 15 项：

- 参数投产 (`need_param_release`)
- 业务参数确认 (`param_confirmed`) — 参数投产选"是"时必填
- 涉及菜单 (`need_menu`)
- 菜单已添加 (`menu_added`) — 涉及菜单选"是"时必填
- 涉及 DIFS (`need_difs`)
- 涉及流程图 (`need_flowchart`)
- 流程图已检查 (`flowchart_checked`) — 涉及流程图选"是"时必填
- 涉及事件平台 (`need_event_platform`)
- 涉及统一任务池 (`need_task_pool`)
- 涉及 BPMP (`need_bpmp`)
- 涉及影像 (`need_image`)
- 涉及 ESF (`need_esf`)
- 涉及交易申调 (`need_trade_tuning`)
- **涉及投产验证 (`need_release_verify`)** — 必填，未选择是/否时直接拒绝保存
- 涉及配置文件投产 (`need_config_release`)

**（4）运维字段（仅运维角色可见可编辑）**

- REL 是否已部署 (`rel_deployed`)
- 是否已完成投产 (`deploy_status`)
- REL 测试状态 (`rel_test_status`) — 默认"否"

#### 步骤 3：引用上次填写（可选）

选中工程后，点击 **「引用上次填写」** 按钮，系统自动查询该工程历史最近一次填写的记录，将以下字段值填入当前表单：`biz_category`、`tech_owner`、`biz_owner`、`common_component_branch`、`flow_definition_name`、`implementation_unit_no`，以及所有检查项（`need_xxx` 系列）。

以下字段**不会被引用**：`flow_name`、`remark`、`requirement_branch`、`is_bug_fix`、`bug_reporter`、`bug_discovery_time`、`rel_test_status`、`need_config_release`。

#### 步骤 4：清空表单

点击 **「清空表单」** 按钮（会弹出确认框），清空后：
- `is_bug_fix` 自动设为"否"
- `rel_test_status` 自动设为"否"
- 工程保留当前选择，投产分支由批次自动填充

切换工程时也会触发清空（保留新选的工程），逻辑同上。

#### 步骤 5：保存与提交

- 研发角色点击 **「提交」** → 先保存所有字段 → 再调用 submit API。**保存时即校验必填字段完整性**，有未填写字段直接拒绝保存并提示缺失项；全部完整则允许保存，再调用 submit API 将行状态变为 `submitted`
- 运维角色点击 **「保存」**（按钮文字变为"保存"）→ 仅保存可编辑的运维字段
- 查看模式下按钮禁用，不可操作

#### 步骤 6：草稿自动保存

表单中任何字段的 `input` 或 `change` 事件都会触发 `localStorage` 自动保存草稿。切换批次或重新打开表单时，自动恢复上次未提交的草稿内容。

### 1.3 实现逻辑

#### 数据模型

- **ReleaseBatch**：投产批次，`release_date` 唯一。状态：`open → closed → executed`
- **ReleaseBatchProject**：批次关联工程，批次创建时从 `ProjectCatalog` 同步
- **ReleaseItem**：投产行项，包含 32 个字段。`line_status`：`draft / incomplete / submitted / confirmed / rejected`
- **ReleaseBranchSequence**：分支序号生成器，`select_for_update` 保证并发安全

#### 行状态自动刷新（`refresh_line_status()`）

每次 `save()` 时调用 `get_missing_fields()` 检查必填字段：
- **18 个核心必填**：`flow_name`、`biz_category`、`project`、`tech_owner`、`biz_owner`、`need_param_release`、`param_confirmed`、`need_menu`、`menu_added`、`need_difs`、`need_flowchart`、`flowchart_checked`、`need_event_platform`、`need_task_pool`、`need_bpmp`、`need_image`、`need_esf`、`need_trade_tuning`
- **4 个条件依赖**：`need_param_release=True → param_confirmed`；`need_menu=True → menu_added`；`need_flowchart=True → flowchart_checked + flow_definition_name`；`is_bug_fix=是 → bug_reporter + bug_discovery_time`
- `requirement_branch`：仅 `sql_only_release=True` 时可为空

**创建/更新时**即调用 `get_missing_fields()` 校验必填字段，有缺失直接 400 拒绝保存。提交时再次校验，完整才允许变为 `submitted`。

#### 字段级权限

通过 `RolePermissionPolicy.release_entry_editable_fields` 控制。前端 `applyFieldPermission()` 根据角色禁用/启用对应字段：
- 研发角色可编辑 30 个研发字段
- 运维角色仅可编辑 `rel_deployed`、`deploy_status`
- 查看模式（`forceViewOnly`）全部禁用

#### 草稿恢复机制

表单所有字段的 `input`/`change` 事件触发 `saveDraftToLocal()`，以 `release_entry_draft:{username}:batch:{batchId}` 为 key 存入 localStorage。切换批次或打开表单时自动调用 `restoreDraftFromLocal()` 恢复。

#### 引用上次填写

API `GET /release-entry/api/items/last-by-project/` 查询逻辑：
1. 按当前工程查询最近一次填写的行项
2. 优先引用**上一个批次**（排除当前批次），回退到所有历史最新记录
3. 前端 `applyLastItemToForm()` 将白名单字段值填入表单，跳过 `is_bug_fix`、`bug_reporter`、`bug_discovery_time`、`rel_test_status` 等独立填写字段

#### 批量修改

仅运维角色可见。勾选行项 → 选择批量字段（`deploy_status` / `rel_deployed`）→ 选择目标值 → confirm 后 POST 到 API，数据库直接批量更新。

#### 表格自定义列

通过 `localStorage` 按用户存储可见列配置。32 个可选列分三组（基础信息 / bug修复 / 检查项），用户可自由勾选。表头固定、序号列和操作列固定在左右两侧，支持横向滚动。

## 二、HOBO 需求登记台账

**访问地址**：`/branch-create/hobo-ledger/`

HOBO 需求登记台账是研发人员记录需求信息的入口，每条登记对应一个需求，系统自动生成规范的分支名称。

### 2.1 研发操作填写流程

#### 步骤 1：打开填写表单

点击 **「填写记录」** 按钮，弹出悬浮表单。

#### 步骤 2：填写登记信息

| 字段 | 必填 | 说明 |
|------|------|------|
| 需求类型 | 是 | REQ / FIX / PUB，决定分支名前缀 |
| 分支名称 | 自动 | 保存后自动生成，格式 `{类型}-{日期}-{序号}`。可勾选"分支添加额外名称"追加自定义后缀（最长 50 字，仅允许中文/字母/数字/下划线/中划线） |
| 工程名称 | 是 | 下拉选择来源 `ProjectCatalog` 中启用的工程 |
| 申请人 | 否 | 留空自动填当前登录用户 |
| 申请日期 | 自动 | 自动填当天日期，不可编辑 |
| 依赖分支 | 否 | 填写了依赖分支则必须填依赖分支联系人 |
| 依赖分支联系人 | 条件必填 | 依赖分支有值时必填 |
| 流程图名称 | 否 | — |
| 提交 UAT 日期 | 否 | — |
| 提交 REL 日期 | 否 | — |
| 投产日期 | 否 | — |
| 需求描述 | 是 | 多行文本 |
| 备注 | 否 | 多行文本 |

#### 步骤 3：保存

点击 **「保存」** 按钮：
- **新建**：调用 create API，系统自动生成分支名，创建成功后关闭表单，刷新列表
- **编辑**：调用 update API，编辑时需求类型和分支名不可修改。仅本人或超管可编辑

#### 步骤 4：搜索与筛选

列表上方支持按以下条件组合筛选：
- 开始/结束日期（默认最近 30 天）
- 需求描述（模糊匹配）
- 需求类型
- 工程名称
- 申请人

### 2.2 按钮含义一览

| 按钮 | 位置 | 含义 | 谁可见 |
|------|------|------|--------|
| **填写记录** | 页面顶部 | 打开表单新增登记 | 有 `hobo_item_create` 权限 |
| **刷新列表** | 页面顶部 | 重新加载工程列表和登记数据 | 所有人 |
| **保存** | 表单内 | 创建或更新登记 | 有编辑权限 |
| **关闭** | 表单内 | 关闭表单弹窗 | 所有人 |
| **搜索** | 列表上方 | 按条件筛选登记记录 | 所有人 |
| **重置** | 列表上方 | 清空所有筛选条件并重新搜索 | 所有人 |
| **导出 Excel（全部）** | 列表上方 | 导出当前数据范围内的全部登记记录，不受筛选条件限制 | 有 `hobo_ledger_export` 权限 |
| **编辑**（行操作） | 表格操作列 | 打开表单编辑登记 | 本人/超管 |
| **查看**（行操作） | 表格操作列 | 弹窗查看全部字段详情 | 所有人 |
| **删除**（行操作） | 表格操作列 | 删除登记，confirm 确认 | 本人/超管 |
| **上一页 / 下一页** | 列表底部 | 翻页 | 所有人 |

### 2.3 实现逻辑

#### 数据模型

**HoboRequirementLedger**：需求登记台账。

核心字段：`requirement_type`（FIX/REQ/PUB）、`requirement_branch`（unique）、`project`（FK → ProjectCatalog）、`description`、`applicant_name`、`applied_date`、`base_branch`、`base_branch_contact`、`flowchart_name`、`uat_submit_date`、`rel_submit_date`、`production_date`、`remark`。

#### 分支名生成规则

保存时后端调用 `ReleaseItem._next_requirement_branch(requirement_type)`：
1. 从 `ReleaseBranchSequence` 表按 `(branch_type, date_str)` 查找或创建序号记录
2. 使用 `select_for_update` 行锁保证并发安全，`current_serial += 1`
3. 生成格式：`{FIX|REQ|PUB}-{YYYYMMDD}-{0001 起始序号}`
4. 如果用户勾选了自定义后缀，追加 `-{suffix}`，最终长度 ≤ 68 字符

#### 依赖分支约束

保存时前端校验：如果 `base_branch` 非空且 `base_branch_contact` 为空，弹出错误提示"已填写依赖分支时，必须填写依赖分支联系人"。

#### 数据范围

列表查询通过 `apply_data_scope(queryset, user, scope_key="hobo_ledger", owner_field="created_by")` 控制，支持 SELF 和 ALL 两种模式。

#### 编辑/删除权限

- 编辑：`item.editable` 由后端判断（本人 || 超管 || 有 `hobo_item_edit_others` 权限）
- 删除：`item.can_delete` 由后端判断（本人 || 超管 || 有 `hobo_item_delete_own` 权限）
- 需求类型和分支名在编辑时不可修改（编辑模式下控件 disabled）

#### 列表补充信息

列表"补充信息"列动态展示非空可选字段的摘要：依赖分支、依赖分支联系人、流程图名称、提交 UAT、提交 REL、投产日期、备注。空字段不展示。

## 三、SQL 执行申请

**访问地址**：`/sql-execute/`

SQL 执行申请是研发人员从 Git 仓库中选择 SQL 脚本提交执行的功能。审批通过后，系统自动连接 MySQL 数据库按阶段顺序执行脚本。

### 3.1 研发操作填写流程

#### 步骤 1：同步 SQL 仓库

点击 **「同步最新仓库」** 按钮，系统从 GitLab 拉取 SQL 仓库（分支 `rel执行且投产SQL`）。

> 页面每 10 分钟自动同步一次。

#### 步骤 2：选择投产日期

在"发起 SQL 执行申请"区域，选择投产日期。日期列表来源于投产征集（ReleaseBatch）中的投产日期。系统默认选中今天及之后最近的一个日期。

#### 步骤 3：选择 SQL 目录

选择投产日期后，系统自动加载该日期对应的 SQL 目录列表（仓库中 `{YYYYMMDD}/` 下的子目录）。选择目录后，下方自动列出目录中所有 `.sql` 文件。

每个文件名旁有 **「预览」** 链接，点击可弹窗查看 SQL 文件内容。

#### 步骤 4：勾选 SQL 文件并确认执行顺序

勾选要执行的 `.sql` 文件后，点击 **「提交执行申请」**，弹出 **「确认 SQL 执行顺序」** 弹窗：

- 列表中条目顺序 = 最终执行顺序
- 可**拖动**条目调整顺序
- 可点击**上移 / 下移**按钮调整
- 可点击**删除**移除条目
- 可点击**添加**在当前条目后插入副本（同一文件可多次执行）
- 可通过顶部下拉框**追加**新文件到列表末尾
- 顺序确认后，点击 **「确认并提交」**

#### 步骤 5：等待机器审批

提交后系统自动执行机器审查（详见 3.3 节），通过则申请状态变为 `pending（待审批）`，失败则弹出具体错误原因。

#### 步骤 6：审批人审批

审批人在列表中看到待审批记录，点击 **「审批并执行」** 即自动启动后台 SQL 执行进程。也可点击 **「拒绝」** 拒绝申请。

#### 步骤 7：查看执行结果

执行完成后，列表中显示状态（成功/失败）。点击：
- **「分文件详情」**：弹窗查看按文件/阶段分段的结构化执行结果（左侧文件列表 + 右侧详细日志），支持"G 风格"字段展示
- **「执行结果详情」**：弹窗查看完整的执行日志文件内容

#### 步骤 8：重新提交（如需要）

已执行成功或失败的记录，申请人可点击 **「重新提交」**：
1. 系统自动设置回原始投产日期和 SQL 目录
2. 加载该目录下最新的文件列表
3. 直接打开顺序确认弹窗，保持原始文件顺序
4. 如原始目录已不存在，提示手动选择

#### 步骤 9：撤回申请

待审批状态的申请，申请人可点击 **「撤回申请」**，状态变为 `rejected`，执行结果标记为"申请撤回"。

### 3.2 按钮含义一览

| 按钮 | 位置 | 含义 | 谁可见 |
|------|------|------|--------|

### 3.3 实现逻辑

#### 数据模型

**SqlExecutionRequest**（唯一模型）：

| 字段 | 说明 |
|------|------|
| `release_date` | 投产日期，必须来自投产征集（ReleaseBatch） |
| `folder_path` | SQL 目录绝对路径 |
| `selected_files_json` | 选中文件的 JSON 数组，按提交顺序 |
| `status` | `pending → approved → running → success/failed` 或 `pending → rejected` |
| `execution_result` | 简短结果描述 |
| `execution_tip` | 实时进度提示 |
| `execution_log` | 完整执行日志（截断至 100K 字符） |

#### SQL 仓库同步（`sql_repo_sync_api`）

1. 从 `GitPlatformConfig` 读取 `sql_repo_path` 和 `clone_url`
2. 定位 `.git` 目录（支持父目录回退查找）
3. 如果仓库不存在或为空 → 从 `clone_url` 克隆
4. 执行 `git fetch origin "rel执行且投产SQL"` → `checkout` → `pull --ff-only`

#### 机器审查（`_machine_review_sql_files`）

提交申请时自动执行，检查规则如下：

1. **UTF-8 编码**：所有文件必须有效 UTF-8
2. **非空**：文件内容不能为空
3. **阶段匹配**：每个文件名必须恰好匹配**一种**阶段类型关键字（不能同时命中多个，也不能一个都不命中）
   - DDL 关键字（默认 `ddl`）
   - 备份关键字（默认 `backup,bak,备份`）
   - 执行关键字（默认 `execute,执行`）
   - 回滚关键字（默认 `rollback,回滚`）
   - 关键字由管理员在后台配置中维护
4. **必须包含执行和回滚**：至少各 1 个文件命中 execute 和 rollback 关键字
5. **USE 语句检查**（如配置了 `sql_db_name`）：每个文件的首条有效 SQL 必须为 `use <db_name>;`（允许中文分号、BOM、行注释）
6. **DDL 规范**：若 DDL 脚本中实际出现 `create table` → 必须为 `create table if not exists`
7. **回滚规范**：若回滚脚本中实际出现 `drop table` → 必须为 `drop table if exists`
8. **顺序规则**：文件顺序需符合管理员配置的提交顺序规则（默认 `backup → ddl → execute → rollback`）

#### 执行顺序确认

前端弹窗支持：
- **拖拽排序**：HTML5 Drag and Drop API，`dragstart/dragend/dragover/drop` 事件
- **上移/下移**：DOM 节点 `insertBefore` 操作
- **添加副本**：同一文件名可插入多次（故意重复执行）
- **删除/追加**：动态维护有序列表

提交时 `selected_files` 以 JSON 数组按列表顺序传给后端，后端按此顺序存入 `selected_files_json`。

#### 阶段识别（`_match_sql_phase`）

根据文件名匹配关键字，每个文件只会被分配到一个阶段。如果文件名同时包含多个阶段的关键字（如同时包含 `ddl` 和 `backup`），则直接拒绝。

#### SQL 执行引擎（`execute_sql_request`）

1. 从 `GitPlatformConfig` 读取数据库配置
2. 验证所有文件路径有效且可读
3. 按文件名关键字识别每个文件的阶段
4. 验证顺序规则
5. 逐文件逐阶段执行：
   - 读取文件 → 分词（状态机按分号分割，处理字符串/注释） → 逐条执行
   - SELECT/SHOW 以"G 风格"记录查询结果（最多 200 行，单格 ≤ 4000 字符）
   - DML/DDL 记录影响行数
   - 异常时 rollback 当前事务，不回滚后续脚本
6. 结果写入 `execution_log` 和磁盘结果文件

#### 后台执行流程

```
用户提交 → PENDING
  → 审批人 approve
    → status=RUNNING, DB 提交
    → transaction.on_commit() 触发独立进程：
      manage.py run_sql_execute_request <request_id>
      → _sql_execute_worker()
        → execute_sql_request() with progress_callback
        → 实时写回 execution_tip + execution_log
        → 完成后写磁盘结果文件
        → status=SUCCESS/FAILED
```

#### 进度轮询

前端检测页面中存在 `status=running` 的记录时，自动启动 1 秒间隔轮询 `/api/request/progress/`，实时展示 `execution_tip` 和 `execution_log`。遇到终态（success/failed/rejected）自动停止轮询并刷新页面。

#### 执行结果解析（`_parse_sql_execution_log`）

将 `execution_log` 文本解析为结构化的文件/阶段分段：
- 识别 `[阶段名]` 标签
- 解析 `开始执行 <文件名>，语句数 N` 和 `执行完成 <文件名>` 标记
- 识别 `无匹配脚本，跳过` 和 `无可执行语句，跳过` 状态
- ERROR/WARN 行关联到当前文件
- 为每个文件条目附加 `g_fields`（阶段、文件名、结果、语句数、日志片段）
- 未被归类的行进入 `orphan_log`（未归类日志）

#### 权限控制

| 操作 | 所需权限 |
|------|----------|
| 访问页面 | `menu_sql_execute` |
| 同步仓库 | `sql_repo_sync` |
| 创建申请 | `sql_request_apply` |
| 审批通过/拒绝 | `sql_request_approve` |
| 自动审批 | 已全局禁用（`_can_auto_approve` 硬编码返回 `False`） |
| 查看他人进度 | `sql_request_edit_others` |
| 删除记录 | `sql_request_delete` 或 本人/超管 |
| 数据范围 | 通过 `apply_data_scope(user, scope_key="sql_requests")` 控制 |

#### 仓库自动同步

页面加载后每 10 分钟（`REPO_AUTO_SYNC_INTERVAL_MS = 10 * 60 * 1000`）自动调用同步 API，页面顶部提示同步结果。
